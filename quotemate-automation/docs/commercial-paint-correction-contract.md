# Commercial paint correction and rich-run review contract

This isolated change implements mobile spec T09/X04 editing authority and closes the separate rich-run approval gap in `lib/sms/quote-review.ts` and migration201. Migration219 remains the price/quiet-Save authority; migration211 remains the released-price guard. No provider or customer send occurs in correction/read routes.

## Native and current web DTO

Owned `GET /api/tenant/commercial-painting/run/:runId/corrections` returns `{ ok: true, snapshot: { runId, extractionId, revision, job_name, site_address, items, corrected_items, released } }`. `extractionId` can be null before extraction. `revision` is a server-computed 64-character SHA-256 over the current editable source and active extraction identity. Metadata is nullable; original/corrected arrays remain separate. Reads never mutate or adopt data.

Owned `POST` to the same path accepts `{ operationId, expectedRevision, extractionId, job_name?, site_address?, corrected_items? }`. IDs are UUIDs; expected revision is 64 lowercase hexadecimal characters. `extractionId` must identify the active extraction (or null for metadata-only updates before extraction). At least one editable field must be present. The entire body is validated before writes. Supplied strings are bounded; null clears job metadata. The takeoff array has 1–5,000 strictly validated rows. Supported units are `m2` and `item`, quantity is finite and nonnegative, coats are integers 1–4, optional height is finite >0 and <30. Surface is nonblank and bounded, room/substrate/system/provenance/notes remain explicit; false/zero are retained. No invalid row is silently dropped.

The operation compares the exact caller-observed revision and latest extraction under a run-first lock, applies all requested fields and clears BOM/priced timestamp/pricing proof together, and stores its immutable outcome in the same transaction. Success is `{ ok: true, status: 'applied', runId, operationId, extractionId, expectedRevision, requestHash, revision }`. This is a confirmed correction, not a priced quote or release. A duplicate exact operation returns the same outcome. Reusing an ID with different inputs rejects. A stale revision returns409 `correction_conflict`; invalid scope/extraction/released input produces no write.

Owned `GET .../corrections?operationId=:uuid` returns the exact stored outcome above or `{ ok: true, status: 'not_found', runId, operationId }`. Absence does not disprove a still-running request; clients keep their opaque receipt and working copy, and never POST on open. The receipt contains scoped IDs/revision/request hash only. After confirmed applied readback, fetch the current snapshot separately: a newer revision is a conflict, not permission to overwrite it with the old outcome.

Current clients retain operation identity before POST, carry the revision from the actual opened snapshot, serialize writes, and keep their working copy through failure/unknown status. Applying assistant edits remains separate from persistence and release. A successful correction must be read back before pricing.

## Legacy PATCH compatibility

`PATCH /api/tenant/commercial-painting/run/:runId` keeps the old payload and success shape. It validates the complete request before any mutation and adapts it to the same atomic transaction using an ingress snapshot. This removes metadata-only partial commits and rejects interleaving after that snapshot. A caller that never supplied its observed baseline cannot receive full stale-client protection; current web/native clients use the new explicit-revision contract. Legacy correction is not evidence that T09 CAS acceptance is complete.

## Rich-run approval

Before unreleased rich-run review, select the actual latest extraction by `(created_at,id)`, require its219 proof and exact persisted timestamp/BOM, re-read current source and verify via the same deterministic219 calculator. Missing proof, newer unpriced extraction, rate/book/GST changes, takeoff edits or old labour provenance make approval unavailable. The returned review version includes that exact extraction/proof/timestamp/BOM binding.

Migration221 replaces only the commercial-paint behavior within the existing release function, preserving other-family behavior. It locks rate/book tables before the run/extraction, checks the actual latest extraction and current219 source against the reviewed proof/timestamp/BOM, and only then invokes the existing explicit release/outbox behavior. No fresh approval can use a historical non-null BOM selected merely by price date. Existing already-released results retain immutable identity and their existing durable delivery recovery semantics; changed rates must not rewrite a released price.

## Required evidence

Actual route tests must cover strict validation before RPC, tenant/operation isolation, exact DTOs, legacy compatibility and GET-only recovery. Actual PGlite tests must exercise all-or-nothing metadata/correction writes, latest-extraction and expected-revision conflicts, repeated/changed operation inputs, replay after a later correction, priced state invalidation, released rejection, and rich-run source/rate/GST/proof/timestamp/newer-extraction races. PGlite serial interleavings are not production multiconnection timing proof. No migrations are applied to a remote database during this work.
# Current caller and price binding

The current web editor reads the actual correction snapshot when opening a run and uses its metadata and items as the displayed baseline. It posts that revision with its operation. The subsequent price request supplies `expectedRevision` from the verified applied outcome. Price ingress compares both the observed revision and the exact job metadata/items to the pricing source sent to the existing 219 persistence function. A correction between these reads rejects before any pricing write; a correction after these reads is rejected by 219's locked source comparison. Omitting `expectedRevision` retains the existing legacy price contract.

The browser retains the exact command and labour intent in AES-GCM encrypted IndexedDB storage with a nonextractable key. Key and ciphertext commit atomically; scope is bound as authenticated additional data. Web Locks protect replacement across tabs. No credentials or customer-contact quote-save inputs enter this copy. Unknown operations have no expiry and mount recovery performs GET only. An explicit retry reuses the exact operation, revision and command. An initial conclusively rejected operation may be marked rejected only when no other attempt was recorded; its working copy remains visible and retained until the user explicitly discards it and reloads current saved data. A validated applied result is retained until the current run is reviewed, or until the original active save flow acknowledges its exact outcome. Browser profile deletion removes local recovery.

# Database definitions, authority and rollback

Migration 221 defines four service-only invoker RPCs: `commercial_paint_edit_snapshot(uuid,uuid)`, `commercial_paint_valid_correction(jsonb)`, `commercial_paint_correction_status(uuid,uuid,uuid)`, and `apply_commercial_paint_correction(uuid,uuid,uuid,text,uuid,text,jsonb)`. It replaces the existing seven-argument `sms_release_quote_resource` definer and the two invoker trigger functions `guard_commercial_quote_extraction()` and `guard_commercial_quote_run()`. Only the release function uses definer execution, preserving its established role boundary for all six rich families; generic quote approval uses its separate contract. Public/anon/authenticated execution is revoked for all seven. Service role can execute the four RPCs and release; trigger functions retain no direct service execute grant and still run through their installed 211 triggers.

The new table has physical columns `tenant_id uuid`, `run_id uuid` (foreign key to paint_runs with delete cascade), `operation_id uuid`, `request_hash text`, `expected_revision text`, `extraction_id uuid`, `changes jsonb`, `outcome jsonb`, and `created_at timestamptz`. Its primary key is `(tenant_id,run_id,operation_id)`; both hashes require 64 lowercase hex characters. RLS is enabled with no public/authenticated policies. Service role receives select/insert, with its existing Supabase BYPASSRLS authority. Operation records have no expiry. Owned run deletion cascades them.

Dependencies are the deployed `paint_runs`, `plan_extractions`, `paint_rates`, and `pricing_book` columns referenced by the full definitions; 211's four enabled triggers and guard capability; 219's proof column and pricing-source function; and 201's exact STRICT IMMUTABLE `sms_normalise_customer_phone(text)` plus the durable `sms_outbox_enqueue(text,jsonb,text)` dependency. Correction writes lock the owned run then latest extraction, update metadata/corrections and invalidate all three pricing fields in one transaction, and insert the operation outcome before commit. Invalid input, stale revision, foreign ownership, released result, reused operation ID or any later SQL error rolls back all writes.

The supplied rollback script is an operational write pause: it replaces only the apply RPC, permits exact committed-operation replay, rejects new corrections, and preserves GET recovery, the operation table, current pricing checks and released-source immutability. It deliberately does not restore unsafe unbound approval or delete recovery evidence. Reapplying 221 restores new correction writes. A historical application rollback without the new reviewed binding leaves fresh commercial-paint approval closed; deploy the paired reader before reopening that workflow.

Ingress accepts only the documented GET query (zero or one operation ID) and no POST query fields. JSON bodies are streamed with a 4,000,000-byte allocation bound and 15-second read deadline. The browser checks the exact serialized UTF-8 request before retaining an attempt or posting. This stays below the [Vercel Functions 4.5 MB payload ceiling](https://vercel.com/docs/functions/limitations). Up to 5,000 ordinary rows fit; a fully populated or Unicode-heavy takeoff may reach the byte bound sooner and is held in the editor with a size error. No rows or notes are silently removed to fit. All rows are validated before any metadata or extraction write. Zero quantities and false switches are preserved; invalid coats are rejected rather than coerced or dropped.
